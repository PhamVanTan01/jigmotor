BugFound=First hardware test (2026-08-04, new product P08, JIG7 + the
    2026-08-04 sensor-swap "new sensor", captured-logs/S2-P08-JIG7-remount0
    {1,2}-test-{1,2}.txt) showed creep making NL WORSE, not better:

    3.46 deg (new firmware, creep on) -- and A36 0.89-0.90 deg -> 1.09 deg.
    Opposite direction from the hypothesis, with
    SweepPointCreepPointsCorrected=344/360 confirming creep WAS actually
    running on almost every point, so this was not "creep did nothing."

RootCause=CreepToUnwrappedTarget pushes its commandPos parameter (aliased
    to the main loop's own `pos`) PAST the nominal targetPos by however much
    extra command was needed to physically drag the real rotor close to
    that target -- correct and necessary for the actual
    Motor_SetElectricalPos() calls it issues. But `pos` is ALSO read at the
    top of the NEXT loop iteration as `signedTargetDeg`'s source (the
    "target" the next point's official 64-sample measurement gets compared
    against). Leaving `pos` at creep's inflated value silently substituted
    "however far we had to command to get there" for "the actual nominal
    grid target" in every subsequent point's own error/NL computation --
    inflating, not correcting, the reported error on nearly every point
    creep touched (344/360).

Fix=One line added at the end of the ENABLE_SWEEP_POINT_CREEP block, after
    all diagnostics are recorded: `pos = targetPos;` -- restores pos to the
    clean nominal grid value (targetPos, the same value already used for
    this point's own ramp+settle, already in scope) before the next loop
    iteration reads it. Does not undo any of creep's real
    Motor_SetElectricalPos() calls or physical rotor motion -- only
    corrects the software bookkeeping variable's downstream meaning.
    Verified this is safe for the NEXT ramp's own use of pos as its
    interpolation start point (RampCommandToTarget always forces an exact
    final assignment to that ramp's own targetPos regardless of start
    point, so this changes ramp SHAPE only, never destination).
    The existing ENABLE_B0B_APPROACH_CREEP call sites (V2-only, unchanged)
    do not have this bug: their commandPos is a separate local variable
    scoped to the approach-leg function, never reused afterward as a
    measurement-target reference the way the main loop's shared `pos` is.
