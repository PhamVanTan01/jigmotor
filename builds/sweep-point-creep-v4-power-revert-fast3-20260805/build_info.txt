WhyV3Failed=v3's 0.6f power was not enough torque against real friction/
    cogging. Real-hardware evidence (v3 test, same P08/JIG7 configuration
    as v1/v2, directly comparable):
      - TotalCorrectionRaw rose to 60368 (vs v2's ~39000) -- each 16-raw
        commanded step achieved LESS real movement at reduced power, so
        more steps were needed to close the same physical gap.
      - SweepPointCreepBudgetExceeded got WORSE: 172/339 = 50.7% (vs v2's
        ~44%), despite the larger 220-raw budget -- the budget increase
        alone could not compensate for the power shortfall.
      - RobustP2P/A36 both regressed most of the way back to old-firmware
        levels: 3.126/0.4229 deg (vs v2's 1.74-1.83/0.31 deg; old firmware
        was 3.05-3.07/0.89-0.90 deg) -- v3 gave back most of v2's gain.
      - Within-batch variance spiked (A2 cv=70.58%, robust_p2p cv=3.92%,
        both far above v2's own run-to-run consistency) -- consistent with
        stick-slip motion (insufficient torque means the rotor sits still
        until commanded position error accumulates enough to overcome
        static friction/cogging, then snaps forward), which also matches
        the user's own independent real-hardware report of MORE
        jerkiness with v3, not less.

Purpose=Isolate the ONE risky variable (power) from the two changes that
    don't carry the same torque risk (step size, budget) -- both of those
    only change how a command is BROKEN UP or how much total correction is
    ALLOWED, not how much torque any single command produces, so they do
    not carry v3's failure mode. This build tests whether step=16/
    budget=220 alone (at full, proven-reliable power) still meaningfully
    reduces heat/jerkiness vs v2 (fewer total commands: v2 needed ~14
    iterations/point average at step=8, this should roughly halve at
    step=16), without v3's reliability regression.
