CodeChange=Core/Src/nonlinear_test.c:
    1) CreepToUnwrappedTarget is now PARAMETERIZED: step/deadband/budget/
       iterations/power are caller-supplied arguments instead of hardcoded
       to the NL_B0B_CREEP_* macros + literal 1.0f. B0-B's own two call
       sites (backoff leg, point-0/forward leg) now pass those exact same
       macros + 1.0f explicitly -- B0-B's behavior is BYTE-FOR-BYTE
       unchanged, verified by scripts/test_b0b_creep_contract.ps1 (updated,
       not weakened, to check the new explicit-argument call pattern).
    2) New tuning constants for the main-sweep-loop call site only
       (NL_SWEEP_CREEP_*, independent of NL_B0B_CREEP_*):
         - Step: 8 -> 16 raw (half the micro-commands for the same total
           correction distance).
         - Budget: 150 -> 220 raw (v2's 150 was sized for B0-B's own
           ~90-120 raw approach-leg gaps; this call site's own gaps run up
           to ~181 raw, so v2 hit SweepPointCreepBudgetExceeded on ~44% of
           corrected points -- 220 comfortably covers the observed max with
           margin, aimed at ~0 BudgetExceeded).
         - Max iterations: 30 -> 15 (resized to match the new step/budget
           ratio -- 220/16=13.75 -- not an independent loosening).
         - Power: 1.0f -> 0.6f (first, deliberately modest cut -- these are
           short final-approach nudges against a much smaller residual gap
           than the original commanded step, not the initial big move).
           NOT yet verified this is enough torque against real friction/
           cogging; WaitForPointSettle still gates every micro-step
           regardless, so an under-powered build would show up as more
           iterations/timeouts, not a silent failure.
       Combined estimate (unverified): roughly half the commands (step)
       times roughly a third of the power-squared heat cost per command,
       so heat per sweep could drop substantially -- needs real hardware
       confirmation, not just arithmetic.
