Purpose=Fix for the "Việc cần làm ngay #1" item in the Q0-Q5 qualification

RootCauseCorrection=The original hypothesis (shared-buffer race between
    LogLine() and LogLineLarge()) was WRONG and was disproven by reading
    the actual implementation before touching any code: both functions use
    separate per-call stack buffers and BLOCKING HAL_UART_Transmit() (not
    DMA), so there is no code-level race that could splice one call's
    buffer into another's. The real defect found: both functions called
    HAL_UART_Transmit() and silently discarded its return value, so a
    failed/partial/timed-out transmission (HAL_TIMEOUT/HAL_BUSY/HAL_ERROR --
    most plausibly caused by USB-serial/PC-side receive buffering, not
    firmware logic) left no trace anywhere in the log. This build does not
    claim to have fixed the underlying transport reliability (the
    receiving-side USB-serial path is outside this firmware's control) --
    it makes failures OBSERVABLE instead of silent.

CodeChange=Core/Src/nonlinear_test.c:
    1) New file-scope counter nlUartTransmitFailureCount, incremented in
       LogLine()/LogLineLarge() whenever HAL_UART_Transmit() != HAL_OK.
    2) Reset to 0 at the start of every CaptureSweep() (one sweep's count
       never leaks into the next).
    3) New END record field UartTransmitFailures=<count>.
    4) END's Status field now reads INVALID whenever
       nlUartTransmitFailureCount > 0, even if measurementValid was
       otherwise true -- a sweep with any dropped/garbled log line cannot
       be trusted point-for-point (DATA/ACQ/MOTION rows for that sweep may
       be truncated or spliced), so it must not read as a valid capture,
       independent of whether the physical acquisition itself was fine.

WhyThisServesNLSync=Per the standing rule (every code change must serve
    JIG1<->JIG4 NL synchronization): the P05 A-B-A cross-jig test (Q3) was
    reported FAIL/CONFOUNDED partly because this corruption silently
    dropped one of the 3 JIG4 official runs, reducing that leg to n=2 and
    lowering confidence in the whole comparison. Analysis tooling could
    only catch this after the fact via manual regex corruption-scanning
    (not automatic). With this fix, any future occurrence sets
    EndStatus=INVALID directly, so the existing RunRole/EligibleForStatistics
    gating in analyze_nonlinear_logs.ps1 and analyze_motor_logs.py already
    excludes it automatically -- no analyzer changes needed.
